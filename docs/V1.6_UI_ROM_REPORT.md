## 一、界面：从"四块摘要卡"到"一份流水"

V1.2 的主页是卡片面板：状态卡、任务卡、最近任务卡。它回答的是「现在什么状态」，
但回答不了「刚才到底发生了什么」——而这个 App 的本质是一条执行流水。

V1.6 直接换成 Codex 那种形式：

```
▌agent runtime  ·  t_8f3a1c       控制台  技能  设置
──────────────────────────────────────────────────────
a11y on   cap on   ovl idle   mdl nb   ime off   cloud -   skills 23   rom MIUI
──────────────────────────────────────────────────────
› 观察当前设备环境                          ← 用户发言块（左侧竖线 + 淡底）

── 运行 ────────────────────────────
● sys.observe  step 1/1                     ← 工具调用（参数压暗）
  ↳ ✓ OK  ·  312ms                          ← 结果（成功绿 / 失败红）
✓ 任务完成：SUCCESS                          ← 收尾横幅
──────────────────────────────────────────────────────
┌─────────────────────────────────┐
│ › 告诉我要做什么…            [运行] │      ← 输入区
└─────────────────────────────────┘
观察环境  截图留证  工具冒烟  技能库  悬浮球
☑ 自动确认              v1.6.0 api30 act40 sk23
```

### 关键取舍

| 决定 | 原因 |
|---|---|
| 正文全部等宽 | 命令、参数、耗时、状态码对齐后能竖着扫，这是终端排版的核心价值 |
| 状态从六枚彩徽章压成一行 `键 值` | 徽章占掉两行高度却只传递 6 个布尔；一行小字信息量相同 |
| 条目用代码拼装而非 XML | 七种条目结构都是「一行等宽文本 + 缩进」，XML 会变成七份重复文件；混排变色（参数压暗）在代码里更好写 |
| 流水上限 240 条 | 一天几千条事件会堆出几千个 View；和终端滚动缓冲区一个道理 |
| 转屏重放事件流 | 流水本身就是状态。旋转后从 `TaskBus.recent()` 重放，而不是清空 |
| 用户往上翻时停止自动滚动 | 用户在看历史，界面不该把他拽回底部 |

### 四个界面一起变深色

只换 `colors.xml` 的语义色值，四个界面（主页 / 控制台 / 设置 / 技能库）同时变，
不留"主页深、设置浅"的割裂。布局里原本只有 3 处硬编码颜色（`#CCD6FFFF`），已同步处理。

## 二、厂商适配：把用户送到门口

标准 Android 只有"申请权限"，国内 ROM 上还叠了三件事：**自启动白名单**、**后台弹出界面**、
**电池优化白名单**。这三样没有统一 API。

`device/RomInfo` 做两件事：

1. **识别**：MIUI / HyperOS / EMUI / HarmonyOS / MagicOS / ColorOS / OriginOS / Flyme / ZUI / One UI。
   依据 `Build.MANUFACTURER` + `ro.miui.ui.version.name`、`ro.build.version.emui`、
   `hw_sc.build.platform.version`、`ro.vivo.os.version` 等属性。
2. **导航**：按 ROM 给出该去哪一页，每个入口带候选 Intent 列表，逐个试，
   全失败退回"应用详情页"——那一步任何 ROM 都能到。

**刻意不做**：不用反射去改系统私有设置（"自启动管理"那类）。那些 API 在多数 ROM 上
要么不存在、要么要系统签名，硬试的结果是随机崩溃。只负责把用户送到门口。

界面上的落点：设置页新增「机型适配」一行，显示当前 ROM；点开是带说明的授权清单。
主页状态条也常驻一个 `rom` 项——用户得能看见"我这台机器为什么和教程不一样"。

### ABI：这次是真支持模拟器了

V1.5 只打 `arm64-v8a`。这意味着 APK 能装进 x86_64 模拟器，但一旦真去加载 native 库就崩——
"能装不能跑"是假支持。V1.6 把 `x86_64` 也打进去：

| 项 | V1.5 | V1.6 |
|---|---|---|
| ABI | arm64-v8a | arm64-v8a + x86_64 |
| APK | 17.9 MB | **36.8 MB** |

代价是体积翻倍（ONNX Runtime 每个 ABI 约 13MB）。取舍理由：宁可大一点，也不要一个
"装得上但跑不动"的包。真要压体积就得上 ABI splits（出两个包），列为遗留项。

## 三、模拟器：装好了，起不来

| 项 | 结果 |
|---|---|
| emulator 37.2.12 | ✅ 安装 |
| `system-images;android-30;aosp_atd;x86_64` | ✅ 安装（3.2GB，官方 CI 精简镜像） |
| AVD `agent_api30` | ✅ 创建 |
| 启动 | ❌ 固件 SVM 未开启 |

诊断链（这部分花了最多时间，两次误判都记在 `docs/EMULATOR_SETUP.md`）：

```
-accel-check  → 6 / hypervisor driver not installed
CPU           → AMD Ryzen 9 7900X，VMMonitorModeExtensions=True（CPU 支持）
固件          → VirtualizationFirmwareEnabled=False（BIOS 里关了）
TCG 兜底      → 5 种组合全失败；qemu 存活时 CPU 时间恒为 0:00:00，设备永远 offline
```

**判断标准修正**：不能看"进程还在"，要看 `adbd 上线 + sys.boot_completed=1`。
launcher 是前端，拉起 qemu 后自己就退出——第一次我把它当成崩溃，第二次又把"qemu 挂着"
当成成功，两次都错。

开启方法（BIOS 里 SVM → Enabled，然后 `--accel auto`）写在 `docs/EMULATOR_SETUP.md`。
脚本已经就位，开完开关一条命令就能起。

### 本轮踩的坑

| # | 坑 | 结论 |
|---|---|---|
| 1 | `emulator ... \| tail` 在后台任务里被判定"完成" | launcher 退出≠模拟器停止；必须看 `adb devices` + `boot_completed` |
| 2 | 用 `capture_output` 跑模拟器 | 子进程被 kill 后仍握着管道，父进程挂死。改文件日志 |
| 3 | `View.setOnScrollChangeListener` 的 lambda 里调 `getChildAt` | 参数类型是 `View` 不是 `ViewGroup`，没有 `getChildAt` |
| 4 | Robolectric 拉 AndroidX 依赖 → AGP 中断 | 需 `android.useAndroidX=true`（仅测试期需要，主 APK 依赖树不变） |
| 5 | Maven Central TLS 被掐 | 换阿里云镜像 |
| 6 | Robolectric NATIVE 图形缺 Windows DLL | Windows 上做不了像素级 UI 测试，只能结构测试 |
| 7 | 测试里写死 dpi 换算像素 | `xxhdpi` 实际 480dpi，按 440 算会让"测的不是目标机型"；改从 `DisplayMetrics.density` 取 |
| 8 | 横屏右栏宽度断言取错父节点 | `statusRow.getParent()` 才是 248dp 面板，再往上是根布局（全屏宽） |

### 失败的那条：按真实测量数据重绘

导出 Robolectric 的视图树（47 个节点，含位置/尺寸/背景色/文字色/字号/文案），
用 Pillow 按这些数字重绘。**结果是错的**：

```
状态条被压成  a.. C.. O.. M.. I.. C.. S.. R..

```

根因：LEGACY 图形模式下 `Paint.measureText` 是桩，42px 的 `agent runtime` 只量出 **13px**。
`wrap_content` 的文字控件宽度整体失真一个数量级，连带 LinearLayout 的剩余空间分配全错。

但在类注释里写明"仅可在支持 NATIVE 图形的环境使用"。

> 教训：**"数据来自真实测量"不等于"画面真实"——测量本身可能就是桩。**

### 模拟器的第二个阻塞

带窗口启动时暴露了一个和虚拟化无关的独立故障：

```
Critical: Failed to load opengl32sw (找不到指定的模块。)
Warning: Software OpenGL failed. Falling back to system OpenGL.
→ 启动器崩溃，qemu 都没被拉起来
```

`emulator/lib64/gles_swiftshader/` 里只有 `libEGL / libGLES_CM / libGLESv2`，**没有 `opengl32sw.dll`**；
换 `-gpu angle_indirect` 报同一个错，说明缺的是**启动器（Qt UI）自己的软件 OpenGL**，不是 guest 的 GL。

所以这台机器上模拟器有**两个独立阻塞**，任缺其一都起不来：
1. 固件 SVM 未开启（需 BIOS 操作）
2. 启动器缺 `opengl32sw.dll`（这个可以补：装一个带该 DLL 的 emulator 版本，或从别的安装里拷）
