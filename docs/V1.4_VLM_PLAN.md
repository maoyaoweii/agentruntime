# 端侧视觉语言模型（SmolVLM-256M）接入状态

> 需求原话：「是视觉小模型和 jev 模型」→ 澄清为「LLaVA 这类型的模型，你挑一个合适的」。
> 本文说明选了什么、做到哪一步、还差什么。

---

## 一、选型：SmolVLM-256M-Instruct

| 候选 | 参数量 | ONNX 体积 | 评价 |
|---|---|---|---|
| **SmolVLM-256M** ✅ | 228M（SigLIP-93M + SmolLM2-135M） | 573MB | 目前最小的标准 LLaVA 架构，能在中端机跑 |
| Qwen2-VL-2B | 2B | ~2GB+ | 中文最强，但要 6GB+ 内存 |
| Moondream2 | 1.86B | ~1GB | 定位专用，英文界面更准 |
| Florence-2-base | 230M | ~500MB | 不是 LLaVA 架构（seq2seq），理解能力弱 |

选它的理由：**架构标准**（image token + projector + decoder，和 LLaVA 一脉），**体积最小**，
且官方仓库 `HuggingFaceTB/SmolVLM-256M-Instruct` 直接提供 `onnx/` 目录，不用自己转换。

关键参数（从官方 config.json 读出来，不是猜的）：

| 项 | 值 |
|---|---|
| 架构 | Idefics3ForConditionalGeneration |
| 视觉编码器 | SigLIP-base，image_size=512，patch=16，hidden=768 |
| 文本解码器 | hidden=576，30 层 |
| image_token_id | 49190 |
| scale_factor | 4（最多 4 个 512×512 patch） |

## 二、已完成（有证据）

| 模块 | 状态 | 证据 |
|---|---|---|
| ONNX Runtime 运行时 | ✅ 已打进 APK | `onnxruntime-android:1.18.0`，arm64 so 约 17MB |
| 分词器 | ✅ 可逆，用真实词表验证 | 49152 词表 / 48900 merges；19 项单测含 6 组往返（中英混排全过） |
| 图像预处理 | ✅ 网格与归一化验证 | 1080×2340 → 1×3 patch；纯白=1.0、纯黑=-1.0、纯红三通道不串位 |
| 模型文件管理 | ✅ 实现 | 目录、完整性校验、缺失原因自述 |
| 会话加载与形状自述 | ✅ 实现 | `VlmEngine.describe()` 输出三个 ONNX 的输入输出名与形状 |
| **生成循环** | ❌ **未联调** | 需要真实权重才能确定张量形状 |

### 分词为什么值得单独做

`tokenizers` 没有官方 Android 绑定，而它错了整条链路就是乱码。所以自己实现 BPE，
并用**官方词表**做了严格验证——尤其是往返一致性（encode 再 decode 必须还原原串），
这一条能同时覆盖 ByteLevel 映射、正则切分、BPE 合并、反向字节还原四个环节。

### 预处理为什么值得单独做

1080×2340 的竖屏截图如果硬切成 2×2，画面会被压扁到无法识别；
按面积约束求解后是 1×3——保持比例，用 3 个 patch 覆盖全屏。
这类几何错误在模型输出上表现为"定位总是偏一点"，极难排查，必须在进入模型前就钉死。

## 三、未完成：生成循环联调

`VlmEngine.generate()` 目前返回 null（上层转成 `VISION_NOT_READY`），因为这三件事
必须看着真实权重才能确定：

### 3.1 确定的形状

放上权重后先跑：

```bash
adb shell am start -n com.agentruntime.agent/com.agentruntime.ui.TaskExecActivity \
  --ez capability_info true --ez finish_after_run false
adb shell run-as com.agentruntime.agent cat files/last_result.json
```

输出里的 `vlm` 段会告诉你模型是否就位。就位后用 `VlmEngine.describe()` 打印三个会话的输入输出，
重点看：

| 会话 | 需要确认 |
|---|---|
| vision_encoder | 输入是 `pixel_values` 还是 `flattened_patches`；形状是 `[1,N,3,512,512]` 还是 `[N*3,512,512]` |
| embed_tokens | 输入 `input_ids` 形状；输出维度是否 576 |
| decoder | `past_key_values.*` 的层数与形状；是否 `use_cache_branch` 分支 |

### 3.2 拼接逻辑

Idefics3 的做法是：文本里放 `image_token_id`(49190) 占位，
用视觉编码器输出**替换**这些位置的 embedding。替换点的索引必须精确——
差一个 token，模型就会把图像特征当成文字读，输出全是胡话。

### 3.3 自回归循环

decoder 每步输出 logits + 新的 KV cache，下一轮把 cache 喂回去。
greedy 解码即可（VLM 定位任务不需要采样）。`MAX_NEW_TOKENS = 96` 是上限。

## 四、模型怎么拿到

权重 573MB，不能打进 APK（安装包会变 600MB 量级，多数分发渠道不接受）。
所以是**运行时内置、权重外置**：

```bash
# 1. 下载（走 hf-mirror，支持断点续传）
python tools/fetch_vlm_model.py --out D:/models/smolvlm

# 2. 推到设备（脚本会打印命令，加 --push 可自动推）
adb shell mkdir -p /sdcard/Android/data/com.agentruntime.agent/files/models/smolvlm
adb push D:/models/smolvlm/*.onnx /sdcard/Android/data/com.agentruntime.agent/files/models/smolvlm/
```

放的是应用外部私有目录，不需要 root，也不需要存储权限。

三个文件：

| 文件 | 体积 | 作用 |
|---|---|---|
| vision_encoder.onnx | 374MB | SigLIP 视觉编码 |
| decoder_model_merged_q4.onnx | 86MB | int4 量化的文本解码器（含 KV cache） |
| embed_tokens.onnx | 113MB | 词嵌入表 |

> 若嫌 573MB 太大，可以只下 decoder + embed（199MB），视觉走无障碍节点——
> 但那样就不是 VLM 了，只是个小语言模型。

## 五、预期性能（未实测，仅供参考）

| 指标 | 估计 | 依据 |
|---|---|---|
| 加载耗时 | 3~8 秒 | 573MB 磁盘读取 + 图优化 |
| 单次推理 | 2~6 秒 | 228M 参数，arm64 CPU，2 线程 |
| 内存峰值 | 1.2~1.8GB | 权重 + KV cache + 中间张量 |

**4GB 内存机型很可能被 LMK 杀掉**。建议在 6GB+ 设备上启用，或者只用它做
"无障碍节点定位失败后的兜底"，而不是每个动作都调用。

## 六、诚实的结论

- **运行时和前端管道是真做了、真测了**：分词 19 项单测全绿，预处理几何验证过。
- **生成循环没跑过**：我在没有权重的情况下无法确定张量形状，硬写就是"看起来能跑"。
- 这不是"差一点"，而是端侧 VLM 最关键的一步——它决定了模型是"看得懂屏幕"还是"输出乱码"。
